# Database and migrations

## Current database

The Projects API uses Neon Postgres through `@neondatabase/serverless`. It reads the connection string from:

1. `DATABASE_URL` (preferred).
2. `POSTGRES_PRISMA_URL` (fallback when `DATABASE_URL` is absent).

The current route uses the `ori_dev_projects` table. It does not run migrations automatically.

## Current schema

Migration file: `db/migrations/001_create_projects.sql`

The migration creates:

| Column | Type | Behavior |
|---|---|---|
| `id` | UUID | Primary key, generated by the database |
| `owner_id` | TEXT | Clerk user ID; required |
| `name` | VARCHAR(60) | Required; at least 2 characters |
| `slug` | VARCHAR(48) | Required; unique per owner |
| `description` | VARCHAR(240) | Required; defaults to an empty string |
| `created_at` | TIMESTAMPTZ | Database-generated creation time |
| `updated_at` | TIMESTAMPTZ | Defaults to creation time; current API does not update it |

The migration also creates an index for listing a user's projects by creation time.

## Applying the initial migration

Apply migrations deliberately to the Neon database assigned to Ori Developer Platform.

1. Confirm the database/project identity in the Neon dashboard.
2. Confirm the target is the intended environment. Do not run production SQL against a development database or vice versa.
3. Review the complete migration file in the repository.
4. Open the SQL editor for the correct database.
5. Run the contents of `db/migrations/001_create_projects.sql`.
6. Confirm that the `ori_dev_projects` table and its index exist.
7. Verify that the Vercel environment for the matching deployment points to this database.
8. Test the Projects API using an authenticated account.

The migration uses `IF NOT EXISTS` for its table and index, so it can be re-applied without recreating those objects. This does not make arbitrary future migrations safe to repeat.

Do not apply a migration automatically as part of a deployment. A production schema change must be reviewed and applied as a deliberate operational step.

## Ownership and data isolation

The API gets the owner ID from the server-side Clerk session. It does not trust an owner ID supplied by the browser.

- List queries filter by the authenticated `owner_id`.
- Inserts use the authenticated user ID.
- The unique constraint prevents one owner from creating two projects with the same generated slug.
- The API currently returns at most 100 projects, newest first.

Any new query that reads or mutates a user-owned record must enforce ownership on the server. Knowing a UUID is not authorization.

## Troubleshooting database responses

| API code | HTTP status | Meaning | Action |
|---|---:|---|---|
| `DATABASE_NOT_CONFIGURED` | 503 | Neither supported connection variable is available | Configure the correct server-side connection string |
| `PROJECTS_MIGRATION_REQUIRED` | 503 | The Projects table is missing | Review and apply the migration to the intended database |
| `PROJECT_NAME_EXISTS` | 409 | The generated slug conflicts with an existing project for this owner | Choose a distinct project name |
| `DATABASE_UNAVAILABLE` | 503 | A database request failed for another reason | Check database availability and server logs without exposing credentials |

An unauthenticated request receives HTTP 401 before the database is queried.

## Backups and recovery

Use the backup and restore facilities provided by the database provider. Before a destructive schema or data change:

- Confirm that a recent recoverable backup exists.
- Document the target database and the expected impact.
- Prefer additive, backward-compatible migrations.
- Plan how the deployed application behaves before and after the schema change.
- Do not assume a Vercel rollback restores database state.

The application currently has no migration runner, migration history table, or automated rollback mechanism.

## Future migration rules

For each new migration:

1. Give it a new, sequential filename.
2. State its purpose and whether it is safe to re-run.
3. Prefer additive changes before removing or renaming existing fields.
4. Include the deployment order and any required backfill.
5. Document verification and recovery steps.
6. Keep the migration isolated to Ori Developer's own database.

Do not point this application at Ori Platform or Ori Intelligence databases as a shortcut.
